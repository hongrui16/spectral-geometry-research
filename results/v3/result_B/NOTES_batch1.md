## E-v3-0b 的第一个实质结论:全秩 RLVR 的 MMLU 崩塌是**格式崩溃**

| ckpt | letter_mass_mean | argmax 在 A/B/C/D | mmlu_letter_logit | top argmax token |
|---|---|---|---|---|
| base | 0.797 | 0.865 | 0.475 | A:59, D:58, B:36, To:23, C:20 |
| e4a_rlvr_full_s0 | **0.023** | **0.025** | 0.240 | **The:109**, We:17, In:8, Scenario:7, A:4 |

该 ckpt 在 v2 交付里的 MMLU = 0.232、GSM8K = 0.494。现在可以确定:它并不是"知识掉到随机",
而是**在答案位置几乎不再输出字母**——落在 A/B/C/D 的概率质量从 0.797 掉到 0.023,
argmax 从 86.5% 命中字母掉到 2.5%,取而代之的是散文开头("The"、"We"、"Scenario")。
letter-logit 式的 MMLU 打分在这种 ckpt 上**测不到知识**,0.24 只是四个字母 logit 排序的残余。

**对 v2 结论的修正**:B 在 v2 交付里把"全秩更新把 MMLU 打到随机、秩受限更新保住 MMLU"
表述为遗忘差异。正确的表述应当是:全秩更新破坏了 MMLU 的作答格式,因此那些格子的 MMLU 数字
不能当作知识度量;秩受限更新(spectrum_matched / random_ext)保住了格式,其 MMLU 才可比。
这正是 v3 §0.3 要求先做 E-v3-0b 再下结论的原因。剩下三个 ckpt(rlvr_spectrum_matched_s0、
sft_full_s0、sft_spectrum_matched_s0)的同组数字出来后,这条判断才算完整 —— 需要看到
spectrum_matched 的 letter_mass 保持在 base 量级,才能把"格式保住 vs 格式崩溃"与
"秩受限 vs 全秩"对上。

## 事故记录:第 50 步评测被主机驱动故障打死(2026-09-13 06:12–06:30)

**现象**:`v3_rlvr_full_lr0.33_s0` 与 `_s1` 分别在两台不同主机上、都恰好在第 50 步失败。
训练本身直到第 50 步都正常(29–37 秒/步),`ckpt_000050` 也写成功了,失败的是
`--eval-every 50` 拉起的评测子进程:`RuntimeError: Found no NVIDIA driver`,
接着 `subprocess.run(..., check=True)` 把训练一并终止。

**根因不是"第 50 步有问题"**,而是主机级故障:*已在运行的进程不受影响,新起的进程拿不到驱动*
(与 v1/v2 记录的同一故障)。worker 启动后第一次 fork 新进程恰好就是第 50 步的评测,
所以故障在那一刻才暴露。含义:每个 run 有 6 次评测 = 6 次撞上坏主机的机会。

**实测标定**(对每台在跑 worker 用新进程试 `torch.cuda.is_available()`):

| 主机 | 组 | 新进程 CUDA |
|---|---|---|
| trial-303095059 / 060 / 063 | maliva A100 | YES |
| trial-303095428 / 429 / 431 | **i2v H100** | **NO**(`nvidia-smi couldn't find libnvidia-ml.so`) |

我为对冲调度延迟拉的三张 i2v H100 **全部**是坏的,属于该池的批次性问题,不是随机衰减。
`v3_rlvr_full_lr0.1_s0` 正跑在其中一台上(第 48 步),到 50 步必死,已主动清掉重排。

**处置**:
1. 杀掉三张 i2v H100 与一台已中毒的 A100;后续只用 maliva/ad_llm 的 A100 组。
2. `worker_queue.sh`:只要 run 的日志出现驱动签名就隔离该 slot,**不论耗时**
   (原本只有 5 分钟内失败才熔断,而这次失败在 23 分钟处,坏主机会继续吃掉整个队列)。
3. `run_one_v3.sh`:释放锁的驱动签名检查从"日志末 40 行"改为扫全文
   (驱动报错被后面的 CalledProcessError 挤出了尾部窗口,导致锁没被释放)。
4. 被打死的 run 全部清空重跑,不保留半截结果。

**代价**:损失约 3 个 run × 50 步的训练时间,无数据损失(这些 run 尚未产出交付物)。

## E-v3-0a 完成:累计位移与累计 KL(18 个 e4a ckpt vs base)

`analysis_v3/cum_kl.py`,32 条 GSM8K 参考序列,fp32、TF32 关。逐矩阵表 3348 行。

| run | ‖ΔW‖_F | KL(base‖ckpt) nats/token |
|---|---|---|
| rlvr full s0 / s1 | 0.755 / 0.755 | **3.73 / 2.04** |
| rlvr frame_matched s0 / s1 | 0.757 / 0.757 | 2.19 / 1.74 |
| rlvr exact_iso s0 | 0.989 | 1.17 |
| rlvr spectrum_matched s0 / s1 | **0.897 / 0.892** | **0.205 / 0.191** |
| rlvr random_ext s0 / s1 | **0.938 / 0.926** | **0.123 / 0.076** |
| sft full s0 / s1 | 3.51 / 3.52 | 0.977 / 0.874 |
| sft frame_matched s0 / s1 | 3.51 / 3.52 | 0.980 / 0.885 |
| sft exact_iso s0 | 3.56 | 0.970 |
| sft spectrum_matched s0 / s1 | 5.63 / 5.63 | 0.717 / 0.678 |
| sft random_ext s0 / s1 | 6.45 / 6.42 | 0.709 / 0.675 |

**读法**:
1. **RLVR 上,秩受限的更新在权重空间走得更远、在函数空间却动得更少**:
   spectrum_matched 与 random_ext 的 ‖ΔW‖ 比 full 大 18–24%,而 KL 小 **10–30 倍**
   (0.08–0.21 对 2.0–3.7)。这把 v3 §3.2 的单步结论(投影更新的 KL 比 full 小两个量级)
   在 300 步的累计尺度上复现了。
2. **frame_matched ≈ full**(‖ΔW‖ 与 KL 都几乎相同),与 scale≈1.0 的事实一致;
   exact_iso 的 KL(1.17)介于两者之间但仍远高于秩受限的两格。
3. **SFT 上同向但弱得多**:秩受限的 ‖ΔW‖ 大 60–83%,KL 只小约 1.4 倍。
4. 与 E-v3-0b 合起来看:秩受限的两格**位移更大、功能变化更小、作答格式完好**;
   全秩三格**位移更小、功能变化更大、格式崩溃**。"等 Frobenius 范数"因此明显不等于
   "等推进",这正是 v3 要修正的协议问题。
5. **注意 seed 方差**:rlvr full 两个 seed 的 KL 是 3.73 与 2.04(差 1.8 倍),
   而秩受限两格的 seed 间高度一致。全秩 run 在 lr×1 下本就处于崩溃区(v3 §2.5),
   这个方差与之自洽,不宜按单 seed 解读。

把所有相邻 ckpt 的 MMLU 跳变按 SE 排序:

| run | step | Δ | 折合 SE |
|---|---|---|---|

0.482/0.477/0.473)。所以正确的说法是:**lr×1/3 这一档的 MMLU 在训练过程中来回摆,
lr×1/10 不摆**。这反而让结论更干净 —— 不稳定是**高 lr 区(接近崩塌边界)的性质**,
而 gate 恰恰要在这个区里做判定。

**这对 gate 是个方法论问题**:health.py 用的是 **step 300 单点** MMLU,判据余量只有 0.03,
而同一个 run 内相邻 ckpt 就能摆 0.06。也就是说 lr×1/3 最终判 HEALTHY 还是 FAIL,
很大程度上取决于**恰好落在哪一个 ckpt 上**,而不是取决于这个 lr 是否真的损害 MMLU。

1. gate 的 MMLU 不要用 step 300 单点,改用**最后若干个 ckpt 的均值**(如 step 200/250/300),
   或至少把单点波动幅度报出来。
2. 之前记录的"两个 seed 不够"仍然成立,而且现在更强:**单个 seed 内部**就不稳。
3. 结合 E-v3-0b(全秩更新的 MMLU 崩塌是**作答格式崩塌**):MMLU 在 letter-logit 协议下
   本就对格式敏感,格式是否稳定可能在 ckpt 之间反复,这与这里观察到的摆动是自洽的。
   step 300 的 `mmlu_format.py` 检验因此更有必要。

1. 长时间复用同一批 worker pod 是有风险的;跨越集群更新窗口后,老 pod 会静默变成

2. 因此**不要**把"pod 还活着"当作"pod 还能用"。`worker_queue.sh` 里每轮循环前的
   `cuda_ok` 自检正是为此,它能挡住老 pod 领取新任务,但挡不住**已经在跑的 run**
   在评测处踩雷 —— 这只能靠 `run_evals` 捕获异常来兜底(已修,见上一节)。
3. 本批的时间线因此是:06:00–11:20 一切正常(4 个 run 顺利完成),11:26–11:50
   驱动更新扫过,3 个在跑的 run 里挂掉 2 个、外加更早重跑的 1 个。

(主机 303096651),这是本批第 5 次。它是当时**唯一还在跑补丁前代码**的 run。

**这里有一个我判断错的地方,记下来**:11:50 我明确考虑过"要不要把 `lr0.1_s2` 杀掉、
用补丁后的代码重启",当时判断是"故障浪潮(11:26–11:50)已经过去、重启代价与期望损失
大致持平",于是决定不动它。**6 分钟后它就死了。** 事后看重启严格更优:
重启只损失约 20 分钟并换来免疫,而实际是既损失了约 25 分钟、又仍然要整轮重跑。
误判的原因是低估了"故障专挑评测时刻发作"这一点 —— 该 run 当时还剩 5 个评测点,
每个都是一次暴露。

**现状(11:57)已收敛**:

| run | step | 主机 | 代码 |
|---|---|---|---|
| lr0.033_s0 | 19 | 303096653 | **补丁后** |
| lr0.033_s1 | 5 | 303099402 | **补丁后** |
| lr0.1_s2(第三次) | 启动中 | 303099400 | **补丁后** |

三个在跑的 run 全部运行在补丁后的代码上,因此**这个故障不可能再让整个 run 丢失**,
最坏情况只是缺一次评测。预计全部完成时间顺延到 **15:20–15:25 UTC**。

**补丁带来的一个连带陷阱(必须记住)**:如果故障恰好发生在 **step-300 的最后一次评测**,
run 会训练完成但没有 `eval_gsm8k.json`,于是 `run_one_v3.sh` 写的是
`FAIL eval missing` 而不是 `DONE`。而 `next_job` 只跳过带 `DONE` 的行 ——
**一个被 FAIL 掉的 run 会被重新领取、从头再跑 3.4 小时,把本来完好的训练结果扔掉**。
一旦出现这种情况,正确处置是:
```
$PY scripts_v3/eval_gsm8k.py --model <run>/ckpt_000300 --limit 500 --out <run>/eval_gsm8k.json
$PY scripts_v3/eval_mmlu.py  --model <run>/ckpt_000300 --limit 1000 --out <run>/eval_mmlu.json
touch <run>/DONE
```
(`ckpt_000300` 是保留的,`--save-ckpt-every 250` 与末步都会留。)
监控 `btrn34fcv` 会把 FAIL 文件的前 120 字符一并报出来,足以分辨
`FAIL eval missing` 与 `FAIL train rc=1`。

### 补丁在实战中生效(首次验证)+ `lr0.033_s0` 所在主机已中毒的处置

**补丁端到端验证通过**。`v3_rlvr_full_lr0.033_s0` 在 step 50 的两次评测都因驱动故障失败,
但**训练没有中断**:

```
[rlvr] step 50 loss -0.0463 30.2s
[eval] step 50 gsm8k FAILED rc=1 -> skipping this eval, training continues
log.jsonl: {"step": 50, "eval_skipped": "gsm8k", "rc": 1}
           {"step": 50, "eval_skipped": "mmlu",  "rc": 1}
```

随后 step 推进到 **53**,`FAIL` 标记不存在。**这是补丁的第一次生产验证:
一个在旧代码下必然变成第 6 次整轮损失的 run,被保住了。**

**但该 run 所在主机 303096653 已经中毒**(驱动错误计数 2)。这意味着:
- 它后续**所有**评测(step 100/150/200/250/300)都会失败 —— 包括最后一次;
- ~~`run_one_v3.sh` 调用 `compute_metrics.py` 时没有加 `--cpu`,该步同样要 CUDA,也会失败~~
  —— **这句是错的,已更正**。`analysis_v3/compute_metrics.py:205` 写的是
  `dev = "cuda" if (torch.cuda.is_available() and not a.cpu) else "cpu"`,
  而**驱动缺失时 `torch.cuda.is_available()` 返回 False 而不是抛异常**,
  于是它**静默降级到 CPU 继续跑**。实测:14:14 开始,到 14:39 已完成 3/15 个 capture
  文件(约 8.3 分钟/个),预计 16:20 左右跑完并正常产出 `metrics.csv`;
- 最终它会以 `FAIL eval missing` 收场,而**训练本身是完好的**(capture 与 ckpt 都正常写出)。

**处置决定:保留这个 run,不重启。** 理由是贵的东西是那 300 步训练与 15 个 capture
(约 26 GB),评测与 metrics 都可以事后从保留的 `ckpt_000300` 与 capture 离线补算
(约 25 分钟)。重启要扔掉已跑的 ~27 分钟,还要承担重新调度的风险,两者总代价接近,
但重启多一层不确定性。

**同时必须堵一个坑**:该 run 的 worker.log 里有驱动签名,所以它结束时
`worker_queue.sh` 会**释放锁并隔离 slot**;而 `next_job` 只跳过带 `DONE` 的行 ——
于是这一行会被别的 worker 重新领取,**把已经跑完的 300 步训练当作垃圾丢掉重跑**。
因此已把该行在 `b_cluster/jobs_v3_train.txt` 里**注释掉**(仓库与 NAS 两份同步),
并在文件里写明原因与恢复方法(去掉注释即可重跑)。

**另两个在跑的 run 主机目前干净**:`lr0.033_s1`(303099402,step 39)、
`lr0.1_s2`(303099400,step 24),驱动错误均为 0。

**待办(它训练完成后,约 15:15)**:需要一个**健康的 GPU worker** 来离线补齐

```
$PY scripts_v3/eval_mmlu.py  --model <run>/ckpt_000300 --limit 1000 --out <run>/eval_mmlu.json
```

## 结论:RLVR 的 lr* = 2e-7(lr×1/10),HEALTHY

三个 seed 全部跑完后的 health.py 判定(base:GSM8K 0.546 / MMLU 0.483):

```
                cfg  n_seeds  gsm8k  mmlu  gsm8k_spread  reward_peak  reward_last100  decline  trunc_frac_last  verdict
 v3_rlvr_full_lr0.1        3  0.640 0.470         0.028        0.586           0.560    0.026            0.139  HEALTHY
v3_rlvr_full_lr0.33        2  0.696 0.452         0.072        0.674           0.657    0.016            0.575  FAIL: mmlu 0.452; spread 0.072
```

**lr\* = 最大的 healthy 档 = lr×1/10 = 2e-7。**

### 逐条余量(正文引用 gate 时应连余量一起给)

| 判据 | lr×1/10 | 余量 | lr×1/3 | 余量 |
|---|---|---|---|---|
| MMLU ≥ 0.453 | 0.470 | **+0.017** | 0.452 | −0.001 |
| GSM8K seed 离散 ≤ 0.04 | 0.028 | +0.012 | 0.072 | **−0.032** |
| decline ≤ 0.030 | 0.026 | **+0.004** | 0.016 | +0.014 |

### 第三个 seed 把结论从"悬"变成了"稳"

只有 2 个 seed 时(14:00 记录),lr×1/10 的 `decline` 是 **0.029**,余量仅 **0.001**,
我当时明确写了"第三个 seed 完全可能把它翻成 FAIL,现在不能宣布 lr\*"。
第三个 seed 跑完后 `decline` 变成 **0.026**,余量扩到 0.004 —— **没有翻,反而更稳**。
这正好构成前面那条方法论观察的一个正例:**2 个 seed 给出的 gate 余量本身就不可靠**,
不是因为它一定偏乐观或偏悲观,而是因为它的不确定度和判据余量同量级。

### 与 A 的 SFT lr\* 的一个重要差别

- A 的 SFT lr\*(1e-6):单点 0.456 / 最后三点均值 0.452 —— **两种读法判定相反**,
  且其中一个 seed(s1 = 0.450)本身就在判据线下,靠跨 seed 平均被拉过线。
- B 的 RLVR lr\*(2e-7):单点 0.470 / 均值 0.472,**两种读法都 PASS**,
  三个 seed 的 MMLU 极差只有 0.008、run 内最大漂移 0.5 SE。

即**RLVR 这一侧的 lr\* 是稳健的,SFT 那一侧的不是**。正文若要并列引用两个 lr\*,
应当说明二者的证据强度不同。

### 三个 lr 档的完整终值

| run | GSM8K | MMLU |
|---|---|---|
| lr0.33_s0 / s1 | 0.660 / 0.732 | 0.444 / 0.460 |
| lr0.1_s0 / s1 / s2 | 0.626 / 0.640 / 0.654 | 0.468 / 0.467 / 0.474 |
| lr0.033_s0 / s1 | 0.562 / 0.562 | 0.477 / 0.481 |
| base | 0.546 | 0.483 |

(lr0.033_s0 的终值是离线从 `ckpt_000300` 补算的,因为它所在主机驱动失效、
6 次在线评测全部被跳过;训练本身完好,见前文。)

**三档的整体图景**:lr×1/30 近乎空操作(GSM8K +0.016,MMLU 持平);
lr×1/10 明显提升 GSM8K(+0.094)且 MMLU 基本不掉(−0.013);
lr×1/3 提升最大(+0.150)但 MMLU 真实下降(−0.031)、两个 seed 不可复现(离散 0.072)、
57.5% 的回答被截断。**健康区的上界落在 lr×1/10。**


HEALTHY = {lr×1/30, lr×1/10} ⇒ **lr\* = 最大的 healthy = lr×1/10 = 2e-7**(与前节一致,未变)。

### 第四次"贴线":lr×1/30 的 decline 余量只有 0.0005

lr×1/30 的 `decline` = **0.02953**,判据 ≤ 0.030,**余量 0.0005**。
至此本项目已出现**四次**判定落在阈值 ~0.001 以内:

| 配置 | 判据 | 值 | 阈值 | 余量 |
|---|---|---|---|---|
| A 的 SFT lr×1/10 | MMLU | 0.456 | 0.453 | +0.003 |
| B 的 RLVR lr×1/3 | MMLU | 0.452 | 0.453 | −0.001 |
| B 的 RLVR lr×1/10(仅 2 seed 时) | decline | 0.029 | 0.030 | +0.001 |
| **B 的 RLVR lr×1/30** | **decline** | **0.02953** | **0.030** | **+0.0005** |

四次独立的"几乎正好压线"**不可能是巧合**。这是前面那条方法论观察的决定性证据:
**这套 gate 的阈值精度超出了本实验规模所能分辨的程度**。judgement 本身没错,
但"HEALTHY / FAIL"这个二值标签**丢掉了它所依赖的全部不确定性**。
正文每次引用 gate 结论,都应当把余量一并给出。

### 一个值得一提的巧合:lr×1/30 两个 seed 的 GSM8K 完全相同

`gsm8k_spread = 0.000` —— 两个 seed 的终值都是 **0.562**(n=500,即都是 281/500)。
这只是巧合,不应解读为"lr×1/30 特别可复现";它的 MMLU 两个 seed 是 0.477 / 0.481,
并不相同。报告时宜写成"离散度低于分辨率",而不是"离散度为零"。

### 必须声明的工具局限:lr×1/30 的稳定性分析只有 1 个 seed

`mmlu_stability.py` 对 lr×1/30 输出的是 `seeds 1`,不是 2:

```
config                       seeds   single    mean3   range  maxSE    single     mean
v3_rlvr_full_lr0.033             1    0.481    0.479   0.004    0.4      PASS     PASS
v3_rlvr_full_lr0.1               3    0.470    0.472   0.008    0.5      PASS     PASS
v3_rlvr_full_lr0.33              2    0.452    0.450   0.026    3.6      FAIL     FAIL
```

原因:`lr0.033_s0` 跑在驱动失效的主机上,6 次在线评测**全部被跳过**,因此它没有任何
`eval_step*_mmlu.json` 中间点;脚本的 `load()` 取不到点就把该 run 跳过了 —— **静默丢弃**。
所以那一行的 `mean3 / range / maxSE` 只反映 `lr0.033_s1` 一个 seed。
(它的终值 0.477 是离线从 `ckpt_000300` 补算的,**进入了 health.py 的 gate 表**,
只是没有中间轨迹。)这个局限必须写明,否则表格会让人以为两个 seed 都被分析了。
